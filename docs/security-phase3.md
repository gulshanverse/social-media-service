# Phase 3 security repair

Admin access tokens are HMAC-signed with the access secret, contain only `sub`, `role`, `sid`, `type: access`, `iat`, `exp`, and `jti`, and expire after 15 minutes. Refresh credentials use a separate secret, contain `type: refresh`, expire after seven days, and are issued only in the `admin_refresh` HttpOnly cookie. The cookie is `Secure` in production, uses `SameSite=Lax`, and is scoped to `/admin/auth`.

Each login creates an `AdminSession` containing only a SHA-256 refresh-token hash. Refresh validates the signature, token type, expiration, active administrator, and session, then atomically replaces the stored hash only when it still matches the presented old hash. Concurrent requests using the same old credential therefore cannot both succeed. Reuse of the previous credential fails. Logout revokes the session, and the access guard checks that session on every request, so existing access tokens immediately stop working after logout. Invalid refresh requests return a generic 401 and clear the cookie.

`JwtAuthGuard` loads the current administrator on every request, so database role changes and deactivation take effect immediately. `RolesGuard` uses the current database role, not stale token claims. Strict global validation rejects unknown request fields. Confession and theme DTOs constrain editable properties and values. Confession editing is pending-only, reports are open-only transitions, and `themeId` consistently means a database Theme ID.

The admin frontend keeps only the short-lived access token in runtime state. It sends credentialed requests so the browser manages the HttpOnly refresh cookie, centrally retries one request after a 401, and returns to login if refresh fails. Confession content is rendered as plain text. API CORS uses exact `WEB_ORIGIN` and `ADMIN_ORIGIN` values with credentials enabled, and Helmet adds baseline security headers. Login rate limiting uses the request IP provided by Express; deployments behind a proxy must configure trusted proxy behavior appropriately. Login and submission rate limiting are process-local and require shared infrastructure in a future multi-instance deployment.
